[165] 2. Executive Summary
[166] The project is a customer-facing GPU and LLM inference platform designed to simplify the process of obtaining GPU-backed inference without requiring customers to manually select infrastructure, configure a GPU instance, install a serving engine, deploy an LLM, or manage the basic inference endpoint.
[167] For the MVP, JarvisLabs.ai supplies the underlying GPU infrastructure. The platform itself does not own the physical GPUs. Instead, it acts as the intermediary and orchestration layer: it collects customer requirements, evaluates available GPU choices, recommends a suitable configuration, requests the resource from JarvisLabs, deploys an open LLM using Docker and vLLM, exposes inference access, and records usage, performance and estimated cost.
[168] The central value proposition is abstraction. A customer should be able to think in terms of workload requirements—model, VRAM, context length, expected concurrency, performance preference and budget—rather than infrastructure commands. The backend translates those requirements into a GPU recommendation and a repeatable deployment workflow.

[211] 3. Problem Statement & Market Landscape
[212] 3.1 The Problem
[213] GPU-backed LLM inference is technically accessible but operationally complex for many customers. A user may need to understand model size, VRAM, quantization, context length, concurrency, GPU availability, serving engines, networking, deployment commands and cost before a single inference request can be processed.
[214] The project addresses this infrastructure and deployment complexity by placing a software mediation layer between the customer and GPU infrastructure. Instead of manually operating a GPU environment, the customer supplies requirements and receives a managed path to an inference-ready environment.

[407] 6. Financial Estimation & Deployment Options
[408] 6.1 LLM Serving Approach
[409] The MVP uses a locally hosted open-weight LLM as an internal AI component of the GPU marketplace. The model is deployed on a GPU resource provisioned through JarvisLabs, while vLLM acts as the model-serving engine. vLLM is responsible for loading and serving the selected model; it is not itself an LLM model.
[410] The proposed deployment environment may use Docker to package the vLLM service, model dependencies and runtime configuration. The marketplace backend can communicate with the locally hosted vLLM endpoint when AI-assisted functionality is required.
[411] The local LLM is intended to support marketplace functions such as:
[412] Natural-language GPU search
[413] Workload understanding
[414] Requirement extraction
[415] GPU recommendation assistance
[416] Comparison explanations
[417] AI assistant conversations
[418] The local LLM is not the GPU rental service offered by the marketplace. GPU rental, payment, provisioning and infrastructure management remain outside the marketplace's referral-layer responsibility.
[419] Serving flow:-
[420] User Query → Marketplace Frontend → FastAPI → Local vLLM Service → Selected Open-Weight Model → AI Response / Structured Requirements → Marketplace Recommendation & Search Layer
[421] 6.2 Supported Open LLM Strategy:
[422] The initial model portfolio should remain relatively small so that the selected models can be evaluated consistently during MVP development. Candidate open-weight model families may include Qwen, Llama and Mistral, with the final model variant selected according to the intended assistant workload, model size, quantization, context length, memory requirement, expected concurrency and available GPU resources.
[423] Model selection should be treated as a configuration and compatibility decision rather than a fixed ranking of model families. A smaller quantized model may require less GPU memory and may be appropriate for lightweight marketplace assistance, while a larger model may require greater memory and compute capacity.
[424] The selection process should consider:
[425] Model quality for the intended marketplace tasks
[426] VRAM requirement
[427] Quantization format
[428] Context length
[429] Response latency
[430] Throughput
[431] Concurrent-request behavior
[432] vLLM compatibility
[433] Available JarvisLabs GPU configuration
[434] License and model usage conditions
[435] 6.3 vLLM Role in the Platform
[436] High-throughput LLM serving: vLLM provides the inference runtime used to serve the selected open model on the provisioned GPU.
[437] Efficient request handling: continuous batching and efficient KV-cache management help improve utilization when multiple inference requests are active.
[438] API access: vLLM can expose an OpenAI-compatible API, allowing the platform to standardize how customer requests reach the deployed model.
[439] Observability: serving health, request latency, TTFT, throughput and error information can be captured where telemetry is available.

[539] 6.9 RAG vs. Direct Model Fine-Tuning

[685] Pricing Model
[686] Cost Basis

[693] GPU-hour / GPU-minute

[700] 7.8.2 Pricing Scope
[701] Pricing scope records the conditions under which a price applies, including provider, model, GPU/resource, region, pricing type, usage type, capacity, currency, and validity period. This prevents the routing engine from comparing prices without the context required to interpret them correctly.
[702] 7.8.3 Estimated vs Actual Cost
[703] Estimated cost is calculated before inference using expected usage, selected model/resource, pricing model, and the applicable provider price. A general representation is: Estimated Cost = Estimated Usage × Normalized Price.
[704] Estimated Cost = Estimated Usage × Normalized Price
[705] Estimated Cost = (Estimated Input Tokens / 1M × Input Price) + (Estimated Output Tokens / 1M × Output Price)
[706] Actual cost is calculated after inference from recorded usage and the provider's applicable billing rules. It may include actual input/output tokens, GPU usage, execution time, request count, minimum billing increments, and other provider-specific conditions: Actual Cost = Actual Usage × Applicable Price.
[707] Actual Cost = Actual Usage × Applicable Price
[708] Actual Cost = (Actual Input Tokens / 1M × Input Price) + (Actual Output Tokens / 1M × Output Price)

[1072] Provider resilience — isolate provider-specific operations behind an adapter.
[1073] Local inference reliability — monitor vLLM availability, errors, latency and resource utilization.

[1078] 11.6 Provider Failure & Automatic Failover
[1079] A provider failure is treated as an operational state transition. The platform records the error/timeout, marks the resource/provider state unhealthy and prevents unsafe reuse. In the current single-provider MVP, there may be no equivalent provider to fail over to; therefore the system should return a controlled error and preserve a clean deployment state. Multi-provider automatic failover is a future capability.

[1294] 14.4 Cost Estimation Formula
[1295] Estimated Infrastructure Cost = Estimated GPU Runtime × Applicable GPU Rate + applicable storage/network/platform charges.
[1296] For a future inference-based pricing layer, an additional normalization can be introduced: Effective Cost per 1M Tokens = Total Execution Cost ÷ Tokens Processed × 1,000,000. This should be based on measured throughput and actual workload assumptions rather than a universal conversion.
[1297] 14.5 Commercial Pricing Position
[1298] For MVP demonstrations, the platform can show provider-derived estimated cost plus an optional proposed service margin. Any commercial rate must be recalculated from the live provider rate card, taxes, discounts, support costs and the desired gross margin.
[1299] 15. Conclusion
[1300] The project is technically and operationally feasible as a JarvisLabs-based GPU/LLM intermediary and orchestration platform. Its MVP does not require ownership of GPU hardware or a full multi-provider marketplace. The immediate objective is to remove infrastructure complexity from the customer workflow.
[1301] The strongest MVP architecture is therefore deliberately focused: React + TypeScript for the customer experience; FastAPI + Python for orchestration; PostgreSQL for structured platform data; AWS Cognito for authentication; JarvisLabs for GPU infrastructure; Docker + vLLM for model serving; Qwen/Llama/Mistral as supported open-model options; and Prometheus/Grafana for observability.
[1302] The design should preserve a clean provider-adapter boundary even though JarvisLabs is the only provider in the MVP. This is the key architectural decision that allows the project to evolve later into a true multi-provider GPU/inference marketplace without redesigning the customer-facing product.
[1303] The supplied project material also establishes a clear future direction: multi-provider integration, intelligent routing, dynamic cost optimization, privacy-aware execution, automated failover, continuous benchmarking and enterprise deployment. These should remain roadmap capabilities rather than being allowed to expand the MVP beyond a deliverable and testable scope.
